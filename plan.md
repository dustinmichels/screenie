# Screenie Clone — Plan

Native Swift/SwiftUI menu bar app. Targets: ~0% idle CPU, <40 MB memory, no full-resolution images held in memory.

## 1. Project setup

- [x] Create Xcode project: macOS App, SwiftUI lifecycle, target macOS 13+
  - Note: project is generated by XcodeGen from `project.yml` (`xcodegen generate`); edit `project.yml`, not the `.xcodeproj`. Entry point: `Screenie/ScreenieApp.swift`. Build: `xcodebuild -project Screenie.xcodeproj -scheme Screenie -derivedDataPath build/DerivedData build`. `@Observable` (sections 2, 5) needs macOS 14; on 13 use `ObservableObject`/`@Published` or raise the target.
- [x] Set `LSUIElement = YES` in Info.plist (no Dock icon, no app menu)
- [x] Decide on sandboxing: off for personal use (simpler), on for App Store distribution (needs a user-picked folder, see section 10)
  - Decision: sandbox **off** (personal-use replacement per README). `ENABLE_APP_SANDBOX: NO` in `project.yml`; no entitlements file. Hardened runtime stays on for notarization (section 12). Sandbox-only tasks in section 10 can be skipped unless this changes.
- [x] Add `.gitignore` for Xcode (`DerivedData/`, `xcuserdata/`, `*.xcuserstate`)
  - Also ignores `build/` (local `-derivedDataPath`) and `.DS_Store`. Generated `Screenie.xcodeproj` stays tracked. Directory is not yet a git repo.

Fresh `UserDefaults(suiteName:)` reads see external `defaults write` changes in-process (verified). Section 9 should observe `folderURL` to restart the query. `PopoverView` placeholder now shows the folder path.

## 4. Detect screenshots

- [x] Start an `NSMetadataQuery` with predicate `kMDItemIsScreenCapture == 1`, scoped to the screenshot folder
  - `ScreenshotWatcher` (`Screenie/ScreenshotWatcher.swift`), main-thread only. `ScreenshotStore.init` creates and starts it for `folderURL`.
- [x] Sort by `kMDItemContentCreationDate`, newest first
- [x] Handle `NSMetadataQueryDidFinishGathering` (initial list) and `NSMetadataQueryDidUpdate` (adds and removals)
  - Both rebuild `items` from the (sorted) query results and call `onChange`, which sets `ScreenshotStore.screenshots`. Element type is `ScreenshotWatcher.Item { url, createdAt }`; section 5 may promote it to `Screenshot`. Verified live: copy-in/rm in a scoped folder updates the list; add latency ~1–3 s (Spotlight import).
- [x] Cap the in-memory list at the newest N items (e.g. 50)
  - `ScreenshotWatcher(folder:limit:)`, default 50; only the first `limit` sorted results are read.
- [x] Fallback: if Spotlight is disabled or indexing lags, use FSEvents/`DispatchSource` on the folder and filter on the `kMDItemIsScreenCapture` xattr
  - Always-on kqueue `DispatchSource` (`.write`) on the folder rescans direct children (bplist bool xattr check) immediately plus one follow-up scan 1 s after the last event (copy-style writers set xattrs after creating the file). Merge in `publish()`: scan authoritative for direct children, query adds subfolder items; Spotlight date preferred. Verified in a `.noindex` folder (Spotlight excluded) and that files without the xattr are ignored.
- [x] Ignore temporary dot-files (`.Screenshot…`) that macOS writes before renaming
  - Scan uses `.skipsHiddenFiles`; query results filtered by `isTemporary` (leading `.`) before the limit is applied. Verified: a `.Screenshot x.png` with the xattr never surfaces; it appears only after the rename.
- [x] Verify: idle CPU stays at ~0% in Activity Monitor with the query running
  - Measured with `/usr/bin/top -pid` on the Debug build watching `~/Desktop/Screenshots` (32 items): 0.0% CPU in every sample, cumulative CPU time 0.45 s → 0.47 s over ~50 s idle, 3 idle wakeups, ~13 MB memory.

## 5. Data model

- [x] `struct Screenshot: Identifiable { url, createdAt }`
  - `Screenie/Screenshot.swift` (`id` = `url`, also `Equatable`); replaced `ScreenshotWatcher.Item` everywhere.
- [x] `@Observable final class ScreenshotStore` that owns the query, the `[Screenshot]` list, and `hasUnseen`
  - Already in place from sections 2–4 (`watcher` owns the `NSMetadataQuery`); now typed `[Screenshot]`.
- [x] Set `hasUnseen = true` when an item newer than `lastSeenDate` arrives
  - `hasUnseen` is now `private(set)` and derived in `updateUnseen()`: newest `createdAt > lastSeenDate`, recomputed on every list change and on `lastSeenDate.didSet`. To clear the dot (section 7), set `store.lastSeenDate = store.screenshots.first?.createdAt` (newest listed date, not `Date()`, so a file still in Spotlight/scan lag isn't silently marked seen). Spotlight `kMDItemContentCreationDate` and file `creationDate` are bit-identical (checked), so mixed sources don't cause false dots. Smoke-tested with a throwaway driver (store + watcher compiled with `swiftc`, `-location` pointing at a `.noindex` folder): pre-existing → off, new copy → on, mark seen → off, newer → on, newer deleted → off.
- [x] Persist `lastSeenDate` in `UserDefaults` so the dot survives relaunch correctly
  - `UserDefaults.standard` key `lastSeenDate`, written in `didSet`. First launch (key missing) seeds it with `Date()` so existing screenshots don't light the dot; later launches load it, so screenshots taken while the app was quit show the dot. Smoke-tested across three launches of a throwaway driver: first → off then on after a new file, relaunch → still on, marked seen → off on next launch.

## 6. Thumbnails

- [x] Create thumbnails with `QLThumbnailGenerator` (or `CGImageSourceCreateThumbnailAtIndex` with `kCGImageSourceThumbnailMaxPixelSize`) at display size × screen scale
  - `Thumbnail.make(url:pointSize:scale:)` in `Screenie/Thumbnail.swift` (ImageIO, in-process, EXIF transform applied, returns `NSImage` sized in points). Display size `Thumbnail.pointSize` = 160 pt longest edge; section 7 grid should size cells to match. Returns nil for non-images (e.g. `.mov`, see section 10).
- [x] Cache them in an `NSCache<NSURL, NSImage>` with a `totalCostLimit` (e.g. 20 MB)
  - `ThumbnailCache` (same file): 20 MiB limit, cost = pixels × 4 bytes; `ScreenshotStore.thumbnails` owns the app's instance. Verified: 200 distinct ~0.87 MB thumbnails → 24 survive (~20.8 MB).
- [x] Generate asynchronously; show a placeholder until ready
  - `ThumbnailCache.thumbnail(for:scale:) async` decodes on a serial `.utility` queue (one decode at a time; re-checks the cache so duplicate requests are free). `ThumbnailView(url:cache:)` in `Screenie/ThumbnailView.swift`: fits its frame (caller sets it), cache hit renders immediately, else gray rounded placeholder + spinner, `photo` icon if undecodable. Section 7: `ThumbnailView(url: shot.url, cache: store.thumbnails).frame(...)`. Verified in a throwaway NSHostingView harness: spinners at t0, images after load, icon for `/etc/hosts`.
- [x] Never decode the full-resolution image for display
  - Display path is only `Thumbnail.make` (no `NSImage(contentsOf:)`/`CGImageSourceCreateImageAtIndex` in `Screenie/`). Measured with `/usr/bin/time -l` on an 8000×6000 PNG: thumbnail peak footprint 13.5 MB vs 195 MB for a full decode. Section 8's copy action is the only intended full decode.
- [x] Drop cache entries for files that were deleted
  - `ScreenshotStore.screenshots` `didSet` removes thumbnails for every URL that leaves the list (deleted, moved, renamed, or past the cap), so section 8's immediate list removal also drops it. `ThumbnailCache.remove` runs on the decode queue, so an in-flight decode can't re-insert the entry. Verified with a throwaway store driver on a `.noindex` folder: both cached → `rm` one → its entry gone, the other kept.

## 8. Per-screenshot actions

- [x] Open in Finder: `NSWorkspace.shared.activateFileViewerSelecting([url])`
  - `ScreenshotActions.revealInFinder(_:)` in `Screenie/ScreenshotActions.swift` (new file; run `xcodegen generate`). Verified via throwaway `swiftc` driver: Finder's selection (osascript) is the revealed file. Wired into UI in the hover/context-menu task.
- [x] Open in the default app on double-click: `NSWorkspace.shared.open(url)`
  - `ScreenshotActions.open(_:)`; `ScreenshotCell` has `.contentShape(Rectangle())` + `.onTapGesture(count: 2)`. Verified in a throwaway `NSHostingView` harness (posts mouse events via `NSApp.postEvent` with ~50–100 ms gaps; `window.sendEvent` without delays does not trigger SwiftUI gestures): double-click on the first cell opened the newest screenshot in Preview.
- [x] Copy image: write `NSImage(contentsOf:)` to `NSPasteboard.general` so it pastes as an image; release it right after
  - Deviation: `ScreenshotActions.copyImage(_:)` writes the file's original bytes under its `UTType` (`public.png`), not an `NSImage`. Measured: `NSImage` path writes uncompressed TIFF and left 281 MB footprint after copying an 8000×6000 PNG (image itself released, the pasteboard client keeps written data until the clipboard changes); raw bytes left 2.7 MB. The pasteboard still offers `public.tiff` (converted on the reader's side): a separate process read PNG/JPEG/HEIC/TIFF/GIF copies back as images via `NSImage(pasteboard:)` and got TIFF data. No decode happens, so section 6's "copy is the only full decode" no longer applies. Residual: the process keeps a copy of the file's bytes until the next clipboard change (36 MB PNG → +35 MB). Non-images (e.g. `.mov`) return false and leave the clipboard untouched.
- [x] Delete: `FileManager.default.trashItem(at:resultingItemURL:)`, and remove the item from the list right away
  - `ScreenshotStore.trash(_:) throws` trashes, then `ScreenshotWatcher.remove(_:)` drops the URL from both sources and publishes synchronously (same path as any list change, so `hasUnseen` and the thumbnail cache follow). On failure it throws and the list is untouched. Verified with a throwaway store driver on a `.noindex` folder: 3 → 2 immediately, file in `~/.Trash`, still 2 after the kqueue rescan; missing file throws (`NSFileNoSuchFileError`), list unchanged.
- [x] Show the actions as hover buttons plus a right-click `contextMenu`
  - `ScreenshotCell` (now takes `store` instead of `cache`): `.onHover` shows a top-trailing material strip on the thumbnail frame with Copy Image (icon flips to a checkmark for 1.2 s on success), Show in Finder, Move to Trash; `.contextMenu` has Open, Show in Finder, Copy Image, divider, Move to Trash. Failed copy/trash beeps. Verified in the harness (window at `.floating` level, cursor warped with `CGWarpMouseCursorPosition` plus a posted `.mouseMoved`): hover renders the strip, clicking copy changes the pasteboard and shows the checkmark then reverts, clicking trash drops the item 3 → 2; the context menu (found via `hitTest` + `menu(for:)`) lists all items and its Copy Image changes the pasteboard. `xcodebuild` succeeds.
- [x] Optional: drag a thumbnail out as a file (`.onDrag` with `NSItemProvider(contentsOf:)`)
  - `.onDrag { NSItemProvider(contentsOf: shot.url) ?? NSItemProvider() }` on `ScreenshotCell`, coexists with the double-click and hover buttons. Verified in the harness (posted down + `.leftMouseDragged` events): a drag session starts, and the drag pasteboard carries a file promise, `public.png` and `public.file-url` for the dragged screenshot. Not verified: an actual drop into Finder/another app (synthetic events can't complete a cross-app drop); whether Finder copies or moves on the same volume is unconfirmed.

## 10. Permissions and edge cases

- [x] Desktop/Documents TCC prompt: the first file access triggers it; handle denial with a message in the empty state
  - Prompt fires on the watcher's first `open`/`contentsOfDirectory` of the folder; `NSDesktop/Documents/DownloadsFolderUsageDescription` added in `project.yml` (Info.plist regenerated). Denial = `CocoaError.fileReadNoPermission` (underlying POSIX EPERM, checked against `~/Library/Mail`). `ScreenshotWatcher.isAccessDenied` + `onAccessChange` → `ScreenshotStore.isFolderAccessDenied`; `refreshFolder()` (popover open, app activation) calls `watcher.retryAccess()` when the folder is unchanged, so granting access later recovers without relaunch. Empty state then shows a lock, "Can't read the screenshot folder", the path, the Files and Folders hint, and an "Open Privacy Settings" button (`x-apple.systempreferences:…Privacy_FilesAndFolders`, not clicked in testing). Found and fixed: Spotlight ignores an unreadable or missing scope and searches the whole disk (probe: 138 results), so `reloadQuery` now drops results outside `folder`. Harness with a `chmod 000` `.noindex` folder: denied + 0 items + message rendered → `chmod 755` + `refreshFolder()` → not denied, 1 item rendered; missing folder → plain "No screenshots yet".
- [x] Sandboxed build: let the user pick the folder with `NSOpenPanel` and store a security-scoped bookmark
  - Not applicable: section 1 decided sandbox **off** (`ENABLE_APP_SANDBOX: NO`), so the app reads the ⌘⇧5 location directly and no picker/bookmark code was added. If App Store distribution is ever wanted, this needs doing first: `com.apple.security.files.user-selected.read-write` + `…files.bookmarks.app-scope` entitlements, an `NSOpenPanel` folder picker replacing `ScreenshotLocation.url()` (the sandbox can't read `com.apple.screencapture` prefs), and `startAccessingSecurityScopedResource()` around the watcher's lifetime.
- [x] Note the floating-thumbnail delay: the file is only written after the preview goes away. Document how to turn it off (⌘⇧5 → Options → Show Floating Thumbnail)
  - `README.md` → "Notes" section (appended below the original prompt text; section 12 rewrites the README and should keep it): explains the ~5 s delay and both ways to turn it off (⌘⇧5 → Options, or `defaults write com.apple.screencapture show-thumbnail -bool false`). This machine has `show-thumbnail` unset, i.e. the default (on). Delay itself not reproduced here (needs an interactive capture).
- [x] Handle screenshots that are renamed or moved out of the folder (the query update removes them)
  - Already handled by the existing design; no code change. Throwaway driver (`ScreenshotWatcher` + a raw `NSMetadataQuery` side by side, 3 copied screenshots) in an indexed `~/…` folder and a `.noindex` one, list checked 0.2 s and 4 s after each move: rename in place → new name replaces old (Spotlight updates the path in place, kqueue scan too); move out → gone; move into a subfolder → kept as `sub/…` via Spotlight (scan covers direct children only; in `.noindex` it drops out); move back in → reappears. All changes visible at 0.2 s. A rename keeps `createdAt`, so no false dot; the old URL's thumbnail is dropped by the `screenshots` `didSet`. Moves out are also covered by the out-of-folder filter added in the TCC task.
- [x] Handle screen recordings (`.mov`) as well, or explicitly filter them out
  - Filtered out: `ScreenshotWatcher.isRecording(_:)` (extension's `UTType` conforms to `.audiovisualContent`) is checked in both the Spotlight results and the folder scan, before the limit, so recordings don't use up list slots. Reason: thumbnails, copy, and the grid are built for still images. Spotlight does report `kMDItemIsScreenCapture = 1` for a `.mov` carrying the xattr (`mdls` confirmed), so without the filter they would show. Verified with a throwaway driver: `shot.png` + `Screen Recording.mov` (xattr copied from a real screenshot) in an indexed folder → raw query lists both, watcher lists only `shot.png`; same in a `.noindex` folder (scan only). A real ⌘⇧5 recording wasn't made (this shell has no Screen Recording permission). README "Notes" mentions it.

## 11. Performance verification

- [x] Idle: CPU ~0%, memory <40 MB (Activity Monitor / Instruments → Allocations)
  - Release build (`xcodebuild … -configuration Release build`), launched with `open -n …/Release/Screenie.app --args -location ~/screenie-perf` (33 copies of the real screenshots, xattrs kept, Spotlight-indexed; the override avoids TCC). `/usr/bin/top -pid` every 10 s for 110 s, popover closed: 0.0% CPU in every sample, cumulative CPU 0.47 s → 0.47 s, 0 idle wakeups, `footprint` 14 MB. After the popover was opened (thumbnails decoded): 32 MB, and back to 0.0% CPU within ~20 s while left open (+0.01 s over 30 s). Found: the ad-hoc-signed Release build re-triggers the Desktop TCC prompt (new cdhash), and until it's answered the main thread sits in `open()` inside `NSMetadataQuery.startQuery` (`ScreenshotStore.init`), so no menu bar icon appears. Section 12's Developer ID signing keeps the grant stable across builds; moving the first folder access off `init` would fix the blank wait.
- [x] With 50 screenshots loaded and the popover open: memory stays bounded by the cache limit
  - Folder topped up to 50 with `cp` copies (`cp` keeps the `kMDItemIsScreenCapture` xattr; Python `shutil.copy2` doesn't). Driven by a temporary hook in `ScreenieApp.swift` (`PerfHook`: signals → `NSApp.activate` + status button `performClick`, and step-scrolling the popover's `NSScrollView` so all 50 cells and thumbnails load; removed at the end of section 11). Footprint: 14 MB idle → 47 MB with the popover open and the grid scrolled to the bottom and back; 4 further open/scroll/close cycles stay at 47–49 MB (plateau, no growth). Breakdown at 47 MB: CG raster data 10 MB (the 50 decoded thumbnails, 320 px P3 RGBA8 ≈ 200 KB each), CoreAnimation 11 MB (layer copies of the rendered thumbnails), MALLOC_SMALL 15 MB (≈ same as with 8 cells visible, i.e. mostly fixed SwiftUI/AppKit cost). The 20 MiB `NSCache` limit never binds at 50 items (≤ 400 KB per thumbnail × 50); the 50-item list cap is what bounds it. Over the plan's 40 MB target while all 50 thumbnails are rendered; `ThumbnailView`'s `@State image` also keeps its own strong reference, so live cells would outlast a cache eviction, and the `MenuBarExtra` window keeps its cells after a close.
- [x] Take 20 screenshots in a row: no growth after the popover closes (Instruments → Leaks)
  - Code change (from an interrupted earlier run, kept): `PopoverView` builds the `ScrollView`/grid only while `isOpen`, so cells of screenshots that left the list while the window was hidden can't survive a reopen; it starts at the top on every open, replacing section 7's `ScrollViewReader.scrollTo(topID)`. Test: Release build + `PerfHook`, folder at 50, "screenshots" written the way `screencapture` does (`cp` of a real one to `.Screenshot….png`, then rename), 20 in a row 1.5 s apart with the popover closed, then 3 open/scroll-to-bottom/close cycles; 3 such rounds (60 new files, every round rotates 20 out of the 50 cap). Closed footprint after the cycles: 46 MB (start) → 49 → 57 → 58 MB; live malloc (`leaks`) 15 281 → 15 463 → 15 465 KB, i.e. flat after round 1; the 46 → 57 MB step is freed-but-dirty `MALLOC_SMALL` pages (dirty 23 MB vs ~15 MB live, peak 60 MB), not live objects. `heap -s` diff over the last round: +40 KB, mostly `NSMetadataItem`s for the extra files in the folder (the query sees all of them; the list stays at 50). `leaks`: 283 leaks / 14 KB, identical after every round, all `NSXPCConnection` "com.apple.linkd.autoShortcut" from AppIntents (system, present at launch); none from Screenie code.
- [x] Detection latency: under 1 s from file write to the dot appearing
  - Release build, popover closed and the dot cleared before each trial; a real screenshot `cp`'d to `.Screenshot….png`, then renamed (what `screencapture` does), timed from the rename to the `hasUnseen` flip logged by `PerfHook`: 19 trials 30–35 ms; plain `cp` to the final name (5 trials): 27–39 ms (`cp` clones the xattrs with the data, so the immediate kqueue rescan already sees them; the 1 s follow-up scan isn't needed). Spotlight plays no part at this speed. One trial per run never flipped: its source (`Screenshot 2026-10-22 at 9.37.13 AM.png`) has no `kMDItemIsScreenCapture` xattr, so it's correctly ignored. The icon swap is the same main-thread SwiftUI update; its draw wasn't timed separately. Not included: the floating-thumbnail delay before macOS writes the file (section 10 note).
  - Section 11 cleanup: `PerfHook` removed from `ScreenieApp.swift` (back to `@State private var store = ScreenshotStore()`); Debug and Release build; `~/screenie-perf` trimmed back to its 50 files.
